## 1. Audit de la chaîne dev → lead-tech → qa

**Granularité : saine.** La chaîne complète a été mobilisée sur les **vrais chunks de code**, pas sur
le doc/copy pur (reformulation logo CLV-50, réalignement de docs). Pas de sur-mobilisation constatée
(l'usine n'est pas sortie pour une vis) ; pas de sous-mobilisation (aucun code n'a shippé sans revue
+ recette). Le rythme « corriger les remarques cheap de la revue, puis committer vert » est le bon :
commits petits, réversibles (`git revert` par incrément), arbre jamais rouge.

**Les revues n'ont pas été des tampons — preuves :** la chaîne a rattrapé des bugs invisibles au
seul typecheck : lien « mes projets » qui sur-promettait, double-transcription, freeze du drag
au-dessus de l'iframe (`setPointerCapture`), **course persist↔engage** (→ verrou par id), et côté
sécu **IP left-most spoofable** + **`sweep()` jamais appelé (fuite mémoire)** dans le rate-limit,
plus la couverture des endpoints payants par le gate. Réflexe **revue sécurité dédiée**
(`factory-security-auditor`) sur du code accès/coût = à conserver comme standard pour tout gate.

**Verdict :** l'organisation de la chaîne est au bon niveau ; les leçons ci-dessous durcissent les
réflexes, elles ne changent pas la structure.

## 2. Ce qui a bien marché (consolidé en règles)

- **Dé-risquage AVANT de coder le risqué.** Sur la fusion, architecte (plan incrémental `docs/26`),
  lead-tech (pré-mortem) et QA (filet de canaris + baseline) ont été lancés **en parallèle AVANT
  toute ligne**. Le pré-mortem a sorti 3 risques bloquants qui ont piloté l'ordre des incréments ;
  un **verrou par id proactif** (« durcissement ») a armé d'avance l'incrément le plus dur. →
  Gravé (voir §4) : `factory-lead-tech` (pré-mortem avant le code à haut risque) et `factory-qa`
  (filet de canaris posé avant de toucher le code risqué).
- **Filet de tests-canaris avant le code risqué** (ex. « transformer pendant un tour en vol » avec
  serveur SSE local prouvant qu'une écriture tardive n'apparaît jamais). → Gravé dans `factory-qa`.
- **Chaîne dev→lead-tech→qa qui attrape de vrais bugs** (cf. §1). → Standard confirmé, pas de règle
  nouvelle nécessaire.

## 3. Frictions rencontrées

- **2e `next dev` sur `apps/web` corrompt le `.next` partagé** → dev server servant du code périmé,
  e2e cassés. **Rencontré DEUX fois** (un dev en vérif, puis la vérif du gate). Fréquent + faux-vert.
- Flake e2e « panne de stockage » sous 6 workers Playwright (SWC natif dégradé sur la machine) →
  `--workers=2`.
- `npm run sync:agents` régénère TOUT le miroir depuis le disque (absorbe des éditions non
  synchronisées d'autres agents — bénin).
- Une revue lead-tech morte sur une erreur API en cours de route → relancée à froid.
- Déviations de spec ponctuelles (CSS Grid au lieu de `position:absolute`) — souvent justifiées.

## 4. Décisions d'amélioration — leçons gravées

Chaque règle nomme le **pire-livrable** qu'elle évite (anti-cargo-cult).

| # | Agent | Règle gravée | Pire-livrable évité |
|---|-------|--------------|---------------------|
| 1 | `factory-qa` | Vérifier contre le serveur de dev **déjà lancé** ; jamais un 2e `next dev` sur un dossier déjà servi | QA prononce « e2e verts / PASS » sur du code périmé servi par un `.next` corrompu → régression shippée avec un faux vert |
| 2 | `factory-developpeur` | Même réflexe en auto-vérif (fondu dans « prouver le comportement ») | Dev déclare un bug « corrigé » après avoir vérifié sur un dev server servant l'ancien code |
| 3 | `factory-qa` | Poser le **filet de tests-canaris AVANT** de toucher un code à haut risque de régression | La régression « écriture tardive qui s'affiche après bascule » ship parce qu'aucun test ne la gardait pendant le dev |
| 4 | `factory-lead-tech` | **Pré-mortem AVANT l'implémentation** d'un changement à haut risque ; les risques pilotent l'ordre des incréments réversibles | La course de flux SSE découverte *pendant* la fusion → un big-bang cousu, non revert-able |
| 5 | `factory-security-auditor` | Pour un gate/rate-limit lié au coût : l'IP de confiance n'est **jamais** le hop client (`X-Forwarded-For` left-most spoofable) ; store éphémère qui **s'auto-purge** | Gate contourné en tournant l'en-tête → crédits Anthropic cramés ; rate-limiter qui fuit en mémoire (`sweep()` jamais appelé) |

## 5. Frictions NON gravées (et pourquoi)

- **Flake Playwright sous 6 workers → `--workers=2`.** C'est une **valeur de projet** liée à cette
  machine (SWC natif dégradé), pas un principe durable. Graver un nombre de workers dans un agent
  serait du sur-ajustement. → Traité comme réglage CI/config (déjà noté en dette CLV-53).
- **`sync:agents` régénère tout le miroir.** Bénin, purement opérationnel ; graver ça dans un agent
  ajoute du bruit sans changer un comportement. → Note pour le manager, pas une règle d'agent.
- **Revue lead-tech morte sur erreur API.** Aléa d'infra transitoire, pas une faute de comportement
  d'agent ; le remède (relancer à froid) est déjà la pratique. → Rien à graver.
- **Déviations de spec (Grid vs `position:absolute`).** Souvent légitimes (jugement d'ingénierie).
  La règle existante de `factory-developpeur` (« signale honnêtement les hypothèses prises ») couvre
  déjà le besoin de re-validation. Ajouter « re-valide toute déviation » sur-contraindrait le cas
  courant. → Non gravé (anti-sur-correction).
